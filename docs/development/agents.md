These instructions apply to AI coding agents and automated development tools working in this repository. Read this file before inspecting or changing code.
1. Product Context
AssistX is a single-installable native Android app, written in Kotlin, with two logical parts:
- a floating assistant;
- an in-app Studio/settings and diagnostics interface.
AssistX is reliability-first. The initial target device reported by the product owner is a Realme Narzo 30 4G, model RMX2156, Android 12, realme UI 3.0, build RMX2156_11_F.19. Verify the actual device/build before making device-specific claims.

The MVP must distinguish:
- what the user wants (desired state);
- current runtime health;
- overlay permission and actual overlay attachment;
- Accessibility enabled and connected state, if Accessibility is required by the approved primary action.
The cause of the existing application's intermittent floating-button/Accessibility failures has not been confirmed. Do not assume Realme background management or battery optimization is the cause without evidence.

3. Source-of-Truth and Conflict Rules
Use this order when deciding how to act:
1. Explicit, recent product-owner instructions.
2. Owner-approved product decisions, scope, and requirements.
3. Owner-approved architecture and platform/security constraints.
4. This AGENTS.md and the applicable approved development workflow.
5. A task-specific plan, provided it does not conflict with the above.
6. Agent assumptions or recommendations (lowest authority).
Platform/security rules are constraints, not optional preferences. An owner request does not authorize bypassing Android security controls.

If documents conflict:
- do not silently choose one;
- identify the conflicting sections/files;
- explain what code or tests would be affected;
- propose the smallest decision needed;
- update the relevant documents only after an approved decision.
4. Mandatory Task Workflow
For each assigned coding task:
Step 1 — Inspect
- Check repository status, current branch, existing changes, and the files involved.
- Read the relevant requirements, architecture, state model, recovery matrix, and tests.
- Do not overwrite, delete, or reformat unrelated work.
- Do not assume all existing files are generated by you.
Step 2 — Plan
Before editing, state:
- task ID and objective;
- relevant requirement IDs;
- expected files/components to change;
- explicitly excluded work;
- dependencies or unresolved decisions;
- acceptance criteria;
- tests to run;
- relevant lifecycle, permission, privacy, and regression risks.
Keep the plan proportional to the task. If one task would change several unrelated subsystems or has no clear pass/fail result, split it.
Step 3 — Implement the smallest change
- Work only on the assigned task.
- Prefer the smallest maintainable implementation that satisfies approved behavior.
- Follow current project conventions.
- Avoid speculative abstractions, future-feature scaffolding, and broad refactoring.
- Do not introduce a new framework, dependency, Gradle module, permission, service, receiver, or network capability without a documented reason and required approval.
- Preserve unrelated edits and user work.
Step 4 — Test
- Add or update tests for behavior changes.
- Run relevant tests and build/static checks available in the repository.
- Run platform/device tests where the behavior depends on Android or the manufacturer.
- Inspect test output and report real results.
- Do not claim tests passed if they were not run.
- If a test cannot run, mark it NOT RUN or BLOCKED and explain why.
Step 5 — Review the diff
Check:
- only expected files changed;
- no accidental secrets, credentials, local logs, databases, build output, or personal data were added;
- no unapproved permission or dependency was added;
- state invariants remain intact;
- no unbounded retry/poll loop was introduced;
- diagnostics are bounded and privacy-conscious;
- documentation and tests match the implementation.
Step 6 — Report
Use the reporting contract in Section 11. Do not claim a task is complete if required evidence is missing.
5. Small-Sprint Rules
- Implement one objective per task.
- Do not implement multiple roadmap milestones in one agent request unless the owner explicitly asks.
- Prefer small vertical slices that include code and tests.
- Do not implement an entire app from one broad prompt.
- Do not advance to the next milestone while its documented exit criteria remain unmet, unless the owner explicitly accepts an exception.
- Keep feature scope small; if a requested task contains multiple independent outcomes, propose a task split before editing.
- If work becomes blocked, stop the affected implementation path and report the smallest decision or technical investigation needed.
Examples of tasks that are too broad:
- “Make the app fully reliable.”
- “Implement all services and the full UI.”
- “Fix all lifecycle bugs.”
- “Build the entire MVP in one change.”
A well-scoped task names one behavior and a testable outcome, for example: “Implement a pure state-mapping function for missing overlay permission and add unit tests for granted, required, and unknown states.”
6. Product and Scope Guardrails
For v0.1, do not add:
- volume controls;
- Wi-Fi or Bluetooth toggles;
- unrelated device quick actions;
- advanced gesture customization or radial menus;
- accounts, backend APIs, cloud sync, or analytics;
- multiple application packages for Studio and Assistant;
- extra themes/animations/personalization beyond the approved UI;
- any feature that does not map to an approved requirement.
A feature being common in other assistive-touch apps is not approval to add it.

The exact primary floating-button action, trigger gesture, button design, minimum Android version, UI toolkit, application ID, distribution method, and reliability targets may remain unresolved until the owner confirms them. Preserve [USER INPUT REQUIRED] placeholders. If a task depends materially on an unresolved choice, ask the smallest necessary question or present a concise recommendation with alternatives; do not silently choose.
7. Android Permission and Platform Guardrails
- Verify current Android behavior from official Android documentation for the relevant API level and target SDK before implementing platform-sensitive behavior.
- Keep AndroidManifest.xml permissions minimal and tied to approved requirements.
- Do not add Accessibility Service declarations unless the approved action requires Accessibility.
- Accessibility must not be used as a generic keep-alive mechanism or for unapproved actions.
- Do not claim that the app can silently re-enable Accessibility or another user-controlled special permission.
- Do not add a foreground service merely to promise that the app remains alive.
- A foreground service must have a valid, documented purpose and comply with applicable service-type, notification, target-SDK, and background-start restrictions.
- Do not add a boot receiver or promise immediate post-reboot startup without approved scope and platform review.
- Never bypass force-stop or other user/system stopping controls.
- Do not introduce device-admin/device-owner, exact alarm, notification listener, usage access, broad file, location, SMS, contacts, or other sensitive access without a new approved requirement.
- Do not claim a particular Realme setting is the root cause without reproducible evidence.
If a current official rule is uncertain, verify it before implementation and record material decisions in the platform constraints or architecture decision log.
8. State, Lifecycle, and Recovery Guardrails
These rules are mandatory:
1. Desired enabled state is not the same as runtime health.
2. An enable request is not proof that startup succeeded.
3. Overlay permission is not the same as overlay attachment.
4. Overlay attachment is not proof that Accessibility is connected.
5. Accessibility enabled is not the same as Accessibility connected.
6. UNKNOWN must remain available when evidence is insufficient.
7. User disablement suppresses automatic recovery.
8. Recovery attempts must be bounded and safe to repeat where practical.
9. Repeated starts must not create duplicate overlays/services.
10. Do not start services or perform lifecycle side effects from UI render/recomposition.
11. Do not restore a persisted ACTIVE value as proof of current runtime health after process recreation.
12. Treat process death, force-stop, and device reboot as different scenarios.
13. Do not report success until the operation has suitable confirming evidence.
14. Do not fabricate a termination event the app could not observe.
15. Diagnostic failure must not normally cascade into core feature failure.
When modifying state/lifecycle code, identify which invariants are affected and add/update tests.
9. Dependencies, Architecture, and Code Quality
- Start with one Android app Gradle module unless a concrete requirement justifies more.
- Do not create an abstraction, interface, manager class, repository, service, or module solely for appearance or future possibilities.
- Avoid both monolithic classes and excessive tiny classes.
- Keep UI, state logic, platform operations, preferences, and diagnostics separated according to the approved architecture.
- Do not introduce a dependency because an AI-generated example uses it.
- For any material new dependency, describe purpose, alternatives, maintenance/security implications, and owner approval needed.
- Do not perform broad dependency upgrades as part of an unrelated feature.
- Follow the actual repository's Kotlin and Gradle conventions.
- Do not hardcode user-facing strings throughout code when Android resources are the established approach.
- Handle errors deliberately; do not swallow important failures silently.
- Do not use !!, broad exception swallowing, or unchecked casts as a shortcut where safer handling is practical.
- Do not add placeholder classes/directories for every future feature.
10. Testing and Evidence Rules
Choose tests according to behavior:
- unit tests for state mapping, recovery decisions, retry limits, preferences, and diagnostics logic;
- Android instrumentation tests for Android-dependent integrations where reliable;
- physical-device tests for overlay, special permissions, service lifecycle, reboot, and Realme-specific behavior.
Always:
- test both success and failure conditions;
- include boundary and repeated-operation cases where applicable;
- run affected regression tests;
- record exact commands/manual steps and results;
- keep unit, emulator, and physical-device evidence distinct;
- report flaky and unrun tests honestly;
- update acceptance/traceability documents when requirements or test coverage change.
Do not weaken or delete a failing test just to obtain a green run. Investigate the failure and make an explicit change with rationale.

12. Documentation and Decision Updates
When approved behavior, component ownership, permission use, lifecycle semantics, storage, or testing changes:
- update the relevant source-of-truth documents;
- update DECISION_LOG.md and/or ARCHITECTURE_DECISIONS.md where appropriate;
- update affected requirement-to-test mappings;
- add migration/compatibility notes if persisted data or external behavior changes.
Do not rewrite the documentation merely to match an accidental implementation. If implementation conflicts with an approved requirement, correct the implementation or raise a decision request.
13. Actions Requiring Explicit Owner Approval
Stop and ask before implementing any change that:
- adds a new user-facing feature or action;
- changes the primary button action or gesture;
- adds a sensitive permission or Accessibility capability;
- adds networking, analytics, a backend, or cloud storage;
- adds a foreground service, boot receiver, or device-admin capability;
- materially changes the architecture, data retention, or privacy model;
- adds a material third-party dependency or framework;
- creates a separate installable app or extra Gradle module;
- changes release/distribution/signing/licensing decisions;
- deletes or overwrites unrelated files or user work.
Small behavior-preserving refactors within a task may proceed if they are proportionate, tested, and do not violate these rules.
14. When Blocked
If the task cannot safely proceed:
1. stop before making speculative or irreversible changes;
2. identify the specific missing decision, permission, environment, or evidence;
3. explain the impact on the task;
4. offer the smallest set of options or a recommended next action;
5. report any safe partial work already completed;
6. do not claim completion.
Do not ask the user to repeat information already present in the repository or approved documents. Search the existing source of truth first.
