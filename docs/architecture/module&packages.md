1. Purpose
This document defines the proposed Android project structure, Kotlin package responsibilities, file-placement rules, test layout, and constraints for adding new code.

The structure supports one installable Android app containing:
- the floating assistant;
- the Studio/settings interface;
- runtime and state coordination;
- platform integrations;
- local preferences and diagnostics.
The design should make component ownership clear without imposing a large enterprise architecture on a small personal-use MVP.

3. Gradle Modules: Start With One
For v0.1, prefer the normal single app module unless a concrete technical requirement demonstrates why a separate module is needed.

Do not create Gradle modules such as :assistant, :studio, :core, :data, or :accessibility solely to mirror logical responsibilities. Those responsibilities can initially be represented by Kotlin packages inside app.

A future module split may be justified by independent reuse, build isolation, security boundaries, or test/build requirements. Any such change must:
1. identify the concrete problem being solved;
2. compare simpler alternatives;
3. document build and dependency impacts;
4. update architecture decisions and tests;
5. receive owner approval before implementation.
4. Kotlin Package Responsibilities
The following packages are proposed boundaries. Names may be adjusted to fit Kotlin conventions and the selected UI toolkit, but responsibilities must remain clear.
4.1 Root package
Purpose: Application entry point and genuinely app-wide setup.

Possible files:
- MainActivity.kt
- AssistXApplication.kt only if application-scoped initialization is required.
Allowed responsibilities:
- initialize minimal application-level dependencies if needed;
- connect the Android entry point to Studio;
- configure app-wide elements that have a clear need for central ownership.
Avoid placing unrelated business logic, overlay code, persistence, and all service control into the Activity or Application subclass.

Do not add an Application subclass simply to hold a global mutable state object.
4.2 ui.studio
Purpose: Studio/settings presentation.

Possible files, added as needed:
- StudioScreen.kt or equivalent screen/view files;
- StudioViewModel.kt only if useful for the chosen UI toolkit and state complexity;
- small reusable status or recovery UI components.
Owns:
- rendering the desired enabled state and observed status;
- handling user input by calling application-facing operations;
- showing permission guidance and recovery instructions;
- presenting diagnostic events when implemented.
Does not own:
- the persistent lifecycle of the floating assistant;
- direct low-level overlay attachment logic;
- duplicate copies of permission/recovery policy;
- startup side effects triggered by every UI recomposition or Activity recreation.
UI toolkit is approved: Jetpack Compose with Material 3.
4.3 ui.floating
Purpose: Visual elements and interaction logic for the floating button, distinct from low-level Android window management.

Possible files:
- FloatingButtonView.kt, a composable, or another view implementation;
- small interaction/state presentation types if needed.
Owns:
- visual representation of the button;
- approved tap/gesture interpretation;
- sending a user action to the relevant application operation.
Does not own:
- the Activity lifecycle;
- raw preference storage;
- independent service restart loops;
- Accessibility service connection management;
- unapproved actions.
If the button's interaction is extremely simple, keep it in one file rather than pre-creating multiple classes.
4.4 runtime
Purpose: Coordinate app activation, deactivation, runtime lifecycle, and bounded recovery.

Possible files, only as the design requires:
- RuntimeController.kt
- RecoveryPolicy.kt
- a narrowly scoped coordinator for starting/stopping the necessary components.
Owns:
- interpreting desired user intent;
- coordinating start/stop requests;
- enforcing idempotency and recovery bounds;
- sequencing operations where ordering matters;
- communicating outcomes to the state layer and diagnostics.
Does not own:
- UI rendering;
- direct user interaction presentation;
- unrelated device features;
- unlimited restart behavior;
- assumptions that Android always permits a start or restart.
If a separate controller and recovery policy add no testability or clarity, use a single well-named class until complexity justifies separation.
4.5 state
Purpose: Define state types and transitions, preferably with minimal Android coupling.

Possible files:
- AssistXDesiredState.kt
- OverlayStatus.kt
- AccessibilityStatus.kt only if relevant
- AssistXUiState.kt or a derived status type where useful
- StateReducer.kt or StateTransitionPolicy.kt only if the transition logic merits a separate unit.
Owns:
- explicit representation of desired and observed states;
- valid state transitions and invariants;
- derived user-facing summaries where appropriate.
Does not own:
- Android window operations;
- Activity or UI framework details;
- persistence technology;
- diagnostic storage I/O.
Do not create many separate enums if a small, well-designed model can represent the states without ambiguity. Conversely, do not collapse distinct conditions into a single isRunning: Boolean.
4.6 overlay
Purpose: Encapsulate Android overlay permission checks and floating-window operations.

Possible files:
- OverlayManager.kt
- OverlayPermissionChecker.kt only if separating the permission adapter improves clarity/testability;
- a narrow status/result type if needed.
Owns:
- checking relevant overlay permission conditions;
- adding/removing the floating window;
- maintaining the single-overlay invariant;
- reporting success, failure, and permission-related outcomes.
Does not own:
- overall desired enabled state;
- Studio UI;
- Accessibility state;
- user-facing policy for every runtime failure;
- unrelated service lifecycle behavior.
Avoid a second class that simply forwards every method to OverlayManager without added responsibility.
4.7 accessibility — Conditional
Purpose: Encapsulate the Android Accessibility Service only if required by the approved v0.1 action.

Possible files:
- a subclass of Android AccessibilityService with a name reflecting its role;
- a narrow status/event adapter if needed.
Owns:
- the minimum approved action requiring Accessibility;
- applicable connection and disconnection callbacks;
- reporting relevant service status where possible.
Does not own:
- overlay creation or removal;
- arbitrary automation;
- unrelated quick controls;
- permission bypasses;
- product-wide state policy.
Do not create this package, manifest service declaration, or Accessibility XML configuration until the owner-approved action requires it and the platform approach has been reviewed.
4.8 data.preferences
Purpose: Read and write local user preferences.

Possible files:
- PreferencesRepository.kt
- PreferencesDataSource.kt only if a real separation is useful;
- a small preferences model if needed.
Owns:
- access to saved desired state and approved configuration;
- safe defaults for missing or invalid values;
- persistence details.
Does not own:
- current runtime-health truth;
- UI presentation;
- service lifecycle policy;
- remote synchronization.
Do not add a database to store one or two simple settings unless requirements justify it.
4.9 data.diagnostics
Purpose: Record and retrieve bounded local diagnostic events.

Possible files:
- DiagnosticEvent.kt
- DiagnosticsRepository.kt
- a storage implementation only when needed by the chosen approach.
Owns:
- event shape;
- local persistence and retrieval;
- retention/size policy;
- best-effort logging behavior.
Does not own:
- permission decisions;
- runtime recovery decisions;
- network transmission;
- arbitrary user analytics.
Diagnostic failures should normally not bring down the primary feature. Avoid logging the same recurring failure at an unbounded rate.
4.10 platform — Optional
Purpose: Isolate an Android-specific adapter only where doing so reduces coupling or makes logic testable.

Potential responsibilities:
- a small wrapper around a specific system API;
- lifecycle/status observation that has a clear independent contract.
Do not create a generic PlatformManager, AndroidHelper, or catch-all utility package. Keep a platform-specific class beside the responsibility it supports unless sharing and reuse justify a separate package.
5. File Placement Decision Rules
When adding a class, the coding agent must ask:
1. What single responsibility does this class have?
2. Which component owns that responsibility according to SYSTEM_ARCHITECTURE.md?
3. Is the class necessary now, or can the behavior live clearly in an existing class?
4. Does the class need Android framework types?
5. Can the core logic be tested without a device?
6. Will the addition create a circular dependency or duplicate existing policy?
7. Is a new package or Gradle module genuinely needed?
Choose the smallest structure that keeps ownership clear and testing practical.
Avoid these patterns
- A huge MainActivity that owns every feature.
- A huge AssistXManager or AppManager that owns all behavior.
- A generic Utils.kt filled with unrelated logic.
- Multiple classes that forward calls without adding behavior or a meaningful boundary.
- Global mutable singletons used to bypass proper state ownership.
- Static/global booleans such as isRunning used as the only health model.
- UI code directly managing persistence, overlay attachment, recovery loops, and diagnostic retention.
- Service classes that directly manipulate unrelated screens.
- Empty packages/classes created for planned future features.
- Separate Gradle modules created only to make the tree look “enterprise-grade.”
6. Android Manifest and Resources
app/src/main/AndroidManifest.xml is the authoritative declaration of application components and permissions.

Rules:
- Add only permissions required by an approved and technically justified feature.
- Explain every sensitive or special permission in the relevant documentation and user flow.
- Do not add Accessibility configuration unless Accessibility is required by the approved action.
- Do not add boot receivers, foreground service declarations, or other lifecycle components merely to try to keep the process alive. Verify whether they are needed and permitted.
- Verify current Android and target-SDK requirements before changing the manifest.
- Do not weaken exported-component settings or add exported components without a documented reason.
- Keep app names, user-facing strings, themes, icons, and other resources in Android resources where appropriate rather than hardcoding user-visible strings throughout code.
- Keep secrets out of manifest metadata and source control.
The actual permission list and service declarations belong in PERMISSIONS_AND_PLATFORM_CONSTRAINTS.md, not in this structural document.
7. Test Package Layout
Mirror the production package structure where useful.

Example:
app/src/test/java/com/nudge/assist/
  state/
    StateTransitionTest.kt
  runtime/
    RecoveryPolicyTest.kt
  data/
    preferences/
      PreferencesRepositoryTest.kt
    diagnostics/
      DiagnosticsRepositoryTest.kt

app/src/androidTest/java/com/nudge/assist/
  overlay/
    OverlayPermissionAndLifecycleTest.kt
  runtime/
    RuntimeLifecycleTest.kt
  accessibility/                         # only if applicable
These names are examples, not mandatory files. Add tests with the behavior they verify; do not generate empty test classes.
Unit tests
Prefer unit tests for:
- state transitions and invariants;
- recovery decisions and retry bounds;
- preference defaults and interpretation;
- event construction and retention policy;
- duplicate-start/stop decision logic.
Instrumentation and device tests
Use Android instrumentation or manual device tests when behavior depends on:
- Android system settings;
- overlay permission;
- actual service lifecycle;
- Accessibility integration;
- reboot and manufacturer background management;
- real window display or interaction.
Document any test that could not be run. Do not label a device-dependent behavior as verified based only on a unit test.
8. Naming Conventions
Use conventional Kotlin naming:
- packages: lowercase, concise, no spaces;
- classes, objects, and interfaces: UpperCamelCase;
- functions and properties: lowerCamelCase;
- constants: follow the repository's established Kotlin convention; avoid introducing multiple competing styles;
- tests: name by behavior or condition, e.g. doesNotCreateDuplicateOverlay;
- state values: use explicit terms rather than vague labels like GOOD, BAD, or RUNNING where they hide distinct conditions.
Names should communicate responsibility and outcome. Avoid vague terms such as Manager2, CommonHelper, DataThing, or Misc.

The application ID/package root must be selected by the owner or recorded as an explicitly temporary development choice:
- Application ID: com.nudge.assist
- Kotlin package root: com.nudge.assist
9. Dependency Rules
- Start with Android/AndroidX and the Kotlin/Gradle tooling needed for the chosen project.
- Add a third-party library only for an identified need that the standard platform or existing dependency cannot reasonably meet.
- Before adding a dependency, document its purpose, size/maintenance/security implications, and alternatives.
- Obtain owner approval for material new dependencies, networking libraries, analytics, dependency-injection frameworks, database layers, or UI frameworks.
- Do not include a dependency merely because an AI-generated template commonly uses it.
- Use the repository's chosen version catalog or dependency convention if one exists; do not create a second competing mechanism.
- Do not upgrade unrelated dependencies during a feature task without an approved reason.
- Keep dependency versions consistent and reproducible according to the project's Gradle configuration.
10. Code Ownership and Cross-Package Calls
Expected call direction:
- ui.studio and ui.floating call application-facing APIs and display supplied state.
- runtime coordinates operations.
- overlay performs overlay/platform operations.
- accessibility performs only approved Accessibility-dependent behavior.
- state defines valid status and transition behavior.
- data.preferences persists user configuration.
- data.diagnostics records and reads diagnostic events.
The implementation may differ where the actual Android lifecycle requires a callback into a coordinator. Such callbacks must be narrow and documented.

Do not let:
- data.* depend on UI packages;
- overlay depend on Studio;
- Accessibility code manipulate Studio views;
- state/domain logic depend unnecessarily on Android UI classes;
- UI recomposition create repeated side effects.
11. Adding, Renaming, or Moving Files
For an assigned coding task:
1. inspect the current structure and existing conventions;
2. identify the narrowest appropriate location;
3. list the expected files in the plan when practical;
4. add only files required by the task;
5. update imports, manifest/resource references, tests, and documentation affected by the change;
6. run relevant build and test commands;
7. report exactly what changed and which checks ran.
Do not mass-rename packages, move unrelated files, delete apparently unused code, or reorganize the whole repository as part of a small feature task. Propose a separate refactor task when restructuring is genuinely needed.
12. Initial Skeleton vs. Later Files
The first project setup should be minimal. Do not create every potential class from this document in advance.
Initial foundation may include
- Android project/build files;
- manifest and app entry point;
- minimal Studio entry screen;
- basic state representation only when required for the first vertical slice;
- tests for code that actually exists;
- root README.md, .gitignore, and AGENTS.md.
Add later, when required
- overlay manager during the overlay sprint;
- runtime coordinator and recovery policy during lifecycle work;
- Accessibility service only after the action decision;
- preferences storage when the first durable setting is introduced;
- diagnostics storage when event requirements are implemented;
- more complex view models, interfaces, or adapters only when justified by complexity or testability.
